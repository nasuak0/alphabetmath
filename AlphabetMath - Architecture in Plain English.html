How AlphabetMath Is Built

A plain-English introduction, written for someone who has never seen the project — or has completely forgotten it. Companion to the interactive Architecture & Flows explorer. v0.11, July 2026.

1What this app actually is

AlphabetMath is a teaching app that runs entirely inside a web browser. There is no server, no login, no database, and nothing is stored anywhere except on the machine you are looking at. When you open it, the whole app arrives at once and then runs by itself.

That single fact drives nearly every other decision in the project. A normal web app is a conversation: your browser asks a server for something, the server answers, back and forth. AlphabetMath has no one to talk to. It is closer to a book than a phone call — everything it will ever show you is already inside it the moment it loads.

The consequences are good ones. It is fast, because nothing waits on a network. It cannot lose your data, because it never sends any. It costs nothing to run. It can be handed to someone as a folder of files. And it can be maintained by one person without a team, which is the actual point.

2The one big idea: one brain, two readers

In the Explorer — the amber Shells & Runtime column. Compare the two flows Boot — no-build (live product) and Boot — Vite build (desktop app): same destination, two routes.

This is the decision everything else hangs from.

All the real code lives in one folder called zmath. Nothing important lives anywhere else. Think of it as the manuscript of a book — the only authoritative copy.

Two separate things know how to read that manuscript. The first is the live product (AlphabetMath - Mobile/index.html), which opens the raw files directly in a browser and translates them on the spot. Nothing has to be prepared, packaged or published first: double-click and it runs. This is what you mean when you say "the app." The second is the packaged build (AlphabetMath - App/), a conventional build setup that reads the very same folder and produces a compact, optimised version suitable for the public internet. Its own entry file is two lines long and contains no app code at all.

Why this, and not the obvious alternative

The obvious alternative is to keep two copies: one you tinker with, one you ship. Everyone tries this. It fails the same way every time. You fix something in the copy you happen to have open, forget to carry it across, and the two versions quietly disagree. Weeks later you are debugging a problem that exists in only one of them, and you cannot remember which one is correct.

Here that is structurally impossible. There is only one copy of the source. The packaged build does not contain app code — it points at the brain. Change a screen and both readers change, because both are reading the same page of the same manuscript. You cannot forget to sync, because there is nothing to sync.

The cost is one rule, and it is absolute: edit only inside zmath. If you ever find yourself editing something in the packaged folder, you have wandered off the path.

3What happens when you open the app

In the Explorer — flow Boot — no-build (live product). It lights up, in order: index.html → @babel/standalone → zmath-loader → esm.sh → main.jsx → app.jsx. That is amber crossing into violet, then blue.

The live product does something slightly unusual, and it explains a whole category of behaviour you might otherwise find mysterious.

Most web apps go through a build step: before anyone can use them, a program chews through all the source files and produces a compressed bundle. You edit, you run the build, you look at the result. It works, but it puts a machine between you and your own work.

AlphabetMath's live version skips that entirely. The browser reads your actual files, as they sit on disk, and translates them the moment they are needed. You save a file and refresh — that is the whole loop.

In order:

  1. The page paints something instantly. Before any code has loaded, the browser already has the stylesheet and shows a placeholder. This is deliberate — the screen is never blank, so a slow load looks like loading rather than like breakage.
  2. A translator arrives. The app's source is written in a convenient dialect browsers do not natively understand. A small translator is fetched from the internet to convert it on the fly.
  3. The files are walked, one leading to the next. Starting from a single entry file, the loader reads it, notices which other files it mentions, fetches those, notices what they mention, and so on until the whole web of files has been collected. Each file is fetched only once, no matter how many others need it.
  4. Each file is translated and rewired. Every file is converted, and its references to its neighbours are rewritten to point at the already-translated versions held in memory. This is the fiddly part, and it is the price of having no build step.
  5. The app starts. The finished entry file is handed to the browser, the app takes over the page, and the placeholder disappears.

There is a safety net around all of this. If something fails during startup, or a screen fails while running, the app catches it and prints the actual error on the page as plain text. This matters more than it sounds: the default behaviour of a broken web app is a white screen that tells you nothing.

One trade-off comes with it. The translator and the app framework are both fetched from the internet at startup, so with no connection the live version shows an error instead of an app. The packaged build has no such dependency — everything is baked in. That is the real reason both readers exist.

4A tour of the parts

In the Explorer — this is the whole diagram, read left to right. Each square below is the color of the column that file sits in.

The whole system, plain name first, real filename after. There are fewer pieces than you would expect, which is itself an achievement.

The front door main.jsx
Ten lines. Starts the app and puts the safety net around it. Both readers arrive here.
The conductor app.jsx
Remembers which screen you are on, swaps screens when you navigate, opens and closes the pop-up panel, and sets the app-wide appearance switches. If behaviour seems to come from nowhere, it usually comes from here.
Home & Topics picker-screens.jsx
The two tile screens: Home's shelves and the Topics grid. Both built on the geometry described in section 6.
The Lab lab-screen.jsx
The Projects screen — a spotlight rail of cartridges. This one came first; the other two were modelled on it.
The parts bin components.jsx
Pieces used all over: the side navigation, the tiles themselves, the pop-up panel, the note reader, the pixel logo.
The icon sheet icons.jsx
Every icon, drawn in code rather than stored as image files. One icon renders in three finishes by changing a setting instead of drawing it three times.
The lesson diagrams figures.jsx
Eight illustrations that appear inside note articles. Drawn by code, so they stay sharp at any size and can be adjusted by changing a number.
The coat check figures-registry.js
A shared list where those diagrams register themselves so articles can call for them by name. Explained in section 7.
The content data.js
Every topic, project, note, article body and exercise — typed directly into the app. This is the book itself.
The cover art tile-covers.js
The artwork on the tiles, stored once and referenced everywhere it appears rather than copied per tile.
The look styles.css, plus five more
One stylesheet that pulls in five others in a deliberate order. Both readers load this one file and nothing else. Order is the whole trick — see section 8.
The tuning knobs tweaks-panel.jsx
A design-time control panel for adjusting the look without editing code. A tool for building the app, not a feature of it.

5How a tap becomes a screen

In the Explorer — flow Navigation — rail → screen → modal. Watch it run from green (components.jsx) through blue (app.jsx) into cyan (picker-screens.jsx) and back out to rose for the content.

Navigating here works differently from most websites, and the difference is intentional.

On a normal site, clicking a link changes the web address, and the address determines what you see. AlphabetMath does not do that. It simply remembers a word — Home, Topics, Projects, Notes, About — and shows whichever screen matches. Changing screens is changing the channel, not driving to a new address. The address bar never moves.

Why give up web addresses? Because this is meant to feel like an app on a tablet, not like a website. There are no shareable links to individual pages, no back-button expectations, no history to manage, no risk of a reload dropping you somewhere unexpected. For a self-contained teaching app, addresses would be pure overhead. A back door exists for testing — you can force a starting screen — but it is a developer convenience, not a feature.

One interaction detail is worth recording, because it will otherwise look like a bug: tiles need two taps. The first selects and highlights; the second opens. On a touch screen with no hover, this gives you a way to look before you leap.

6Why nothing ever rearranges

In the Explorer — flow Fixed-canvas tray scaling. Five nodes across blue, cyan and slate: app.jsx → picker-screens.jsx → lab-screen.jsx → picker.css → lab.css.

This is the heart of the project's visual identity, and the decision most likely to be undone by accident.

Ordinary web pages are elastic. Make the window narrower and the content reflows — columns collapse, things stack, text rewraps. That is a sensible default for documents. It is the wrong behaviour for this app.

AlphabetMath's screens are drawn once at one fixed size — a canvas 980 by 612 units — and the whole picture is then scaled up or down to fit your window, like a photograph or a television image. Every element keeps its exact position and proportion relative to every other element. A tile is always 218 by 162 units. Nothing ever moves to a new place because the window changed.

Why accept the constraint? Because you are designing a physical-feeling object — a shelf of cartridges. Physical objects do not rearrange themselves when you step back from them; reflowing layouts would break the illusion instantly. It also means what you see while designing is exactly what everyone sees, at every size, with no surprises.

Two refinements sit on top. First, the picture grows only to a point — about 1.6 times its natural size — then stops and centres itself with margin; without that cap, a large monitor would inflate the tiles to absurdity. Second, the composition is tuned so that at full width you see a sliver of the next tile at the edge of the shelf. That peek is not decoration: it tells you there is more to scroll to, without a scrollbar or an arrow.

One rule must not be broken. The tray and the tiles inside it scale as one unit — the tiles are part of the picture, not stickers stuck on top of it. If they are ever separated, the tiles will drift out of alignment with the tray at some window sizes and the illusion collapses. Resizing tiles is fine; separating them is not.

7Two patterns worth recognising

The coat check

In the Explorer — flow Note figures — registry pattern, ending at the rose node figures-registry.js.

An article in the app is written as a list of pieces: a heading, some paragraphs, a diagram called lattice, more paragraphs. But lattice is just a word in a text file — something has to connect that word to the actual drawing.

The solution is a shared list, like a coat check. When the app starts, every diagram hangs itself up and leaves its name on the hook. When an article asks for lattice, the reader collects it by name. Neither side needs to know about the other, and adding a new diagram requires no changes anywhere else.

Why this is a named pattern rather than an obvious one: the earlier approach relied on files loading in exactly the right order, which is fragile and fails in ways that are miserable to diagnose. The coat check has one clear owner and no ordering requirement at all.

Flipping a switch instead of repainting the room

In the Explorer — flow Tweaks → live restyling: app.jsx → tweaks-panel.jsx → tweaks-overrides.css → tokens.css.

The app can change its whole appearance — materials, finishes, spacing modes — instantly. It does this by writing a small label onto the page, something like "material: flat." The stylesheet is watching for those labels and restyles everything accordingly.

The alternative would be for the code to hand every individual element its own appearance instructions, meaning every element has to be rebuilt whenever anything changes. Here the code flips one switch and the styling system does the rest, instantly and without rebuilding anything. It also keeps a clean boundary: code decides what state the app is in; the stylesheet decides what that looks like.

8Why the stylesheet order matters

In the Explorer — the slate Style Cascade column, far right. The numbers on its wires (1 through 6) are the loading order described below.

Six stylesheets load in a fixed sequence, and the sequence is a genuine contract rather than an accident of history. Later sheets can override earlier ones, so the order is a hierarchy of authority:

  • Foundations — the colours, sizes and spacings everything else refers to. Change one value here and it propagates everywhere.
  • Layout and chrome — the frame of the app: navigation, stage, pop-ups, the note reader.
  • Materials — the moulded look of the tiles.
  • The Lab, then Home and Topics — screen-specific styling, in that order, because the two picker screens inherit their base look from the Lab.
  • Overrides — last, and therefore able to overrule anything above. This is where the tuning switches from section 7 take effect.

The practical takeaway: a new stylesheet is added to that one list, never to a reader. If styling were added to the live product's page, the packaged build would not have it, and the two would look different. Same principle as the brain — one place, no drift.

9Two things to keep an eye on

In the Explorer — both appear as orange risk cards under Patterns & risks, below the diagram.

A tool nobody picks up. There is a file of reusable diagram parts that was updated during a past reorganisation but is referenced by nothing. It never loads and has no effect on the running app. It is not harmful — but it looks alive, so a future reader (including you) may waste time studying it. Either wire it in or delete it.

The startup dependency. As covered in section 3, the live version needs the internet at the moment it loads. If it were ever used somewhere without a reliable connection, the packaged build is the answer — it carries everything with it.

10Glossary

These are the words the interactive explorer uses, and what they mean. The square shows which layer each word belongs to.

The brain
The one folder holding all the real code. Everything else points at it.
Shell / reader
A wrapper that knows how to start the brain. There are two.
Thin adapter
A file that contains no logic of its own — it just connects one thing to another.
Module
One source file. "The import graph" is the web of which files call for which others.
Import / dependency
One file saying "I need something from that other file."
Build step
Preparing and packaging code before anyone can run it. The live version does not have one.
Compile / transform
Translating the source dialect into something the browser understands.
Entry point
The first file that runs. Everything else is reached from it.
State
Something the app is currently remembering — such as which screen you are on.
Component
A reusable piece of interface with its own appearance and behaviour. A tile is one.
Render / mount
Drawing a component onto the screen for the first time.
Router / routing
Using the web address to decide what to show. This app deliberately does not do it.
Registry
The coat check — a shared list things add themselves to so others can find them by name.
Side effect
A file that does something merely by being loaded, rather than by being called.
Static data
Content typed into the app itself instead of fetched from a server.
Cascade
The rule that later styling can override earlier styling. Why sheet order matters.
Token
A named value — a colour, a size — referred to by name, so one edit changes everything using it.
Fixed canvas
Designing at one exact size and scaling the result, rather than letting it reflow.
Reflow / responsive
Content rearranging itself to fit the window. Standard on the web; avoided here.
Viewport
The visible area of the window.
Error boundary
The safety net that prints a real error instead of showing a blank white screen.
Guard / gate
A check that blocks the app until a condition is met — correct screen size, correct orientation.
Portal
Placing something outside the app's normal container, so it can sit over the top of everything.
Backend / API
A server the app talks to. This project has none, by choice.

11If you remember only five things

  1. Edit only inside the brain. All real code lives in zmath. Both readers point at it. Editing anywhere else creates the drift this whole structure exists to prevent.
  2. There is no server and no build. The app is a self-contained object. It loads whole and runs alone.
  3. Screens are pictures, not layouts. Drawn once at a fixed size and scaled. Nothing reflows. The tray and its tiles scale as one unit — never separate them.
  4. Content is typed in, not fetched. Every topic, note and exercise sits in one content file. Adding a lesson means editing that file.
  5. Appearance is switches, not instructions. Code sets a label; the stylesheet decides what it looks like. Look for styling problems in the stylesheets, not the code.
